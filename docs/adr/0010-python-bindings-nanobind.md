# ADR-0010: Python bindings: nanobind, one module per C++ module, one public package `libspeech`

- **Status:** accepted
- **Date:** 2026-09 to 2026-10
- **Source:** checklist.md (public import path, module naming), CONTRIBUTING.md (type stubs), commits 9680dbe, a6851f8, 7ba1ab7

## Context

The Python API must mirror the C++ API, be fast on NumPy data, and import as `libspeech`, not as private module names.

## Decision

- nanobind (`nanobind>=2.2.0` to build, needed for the free-threading flag). Each C++ module gets `speech_<name>_py` from `src/bindings/python/bind_<name>/`, found automatically, plus a `tests/python/test_<name>.py` and one `add_python_test(<name>)` line.
- The public package is `libspeech`; its `__init__.py` preloads the runtime libraries and re-exports. The compiled modules cannot be imported on their own.
- Runtime library file names are baked into an `_about` module by CMake (`$<TARGET_FILE_NAME:...>`), because `ctypes` loads them directly and RPATH does not help (commits a6851f8, 9680dbe).
- Type stubs (`py.typed`, one `.pyi` per module) are generated by `python -m nanobind.stubgen` in the build; a module that cannot be imported fails the build. Pure-Python files carry inline annotations.
- NumPy in and out have fast paths; `Audio` supports NumPy and DLPack without copying (ADR-0018). The GIL is released during long native calls.

## Rejected alternatives

None recorded in the history.

## Consequences

- A new Python-visible function must be registered in the stubs build and in `__all__`.
- After adding a test file or a module, re-run CMake: the build tree can keep a stale file list.
